## 2. ⚙️ Как работает система: workflow в n8n

Система устроена как **retrieval + reasoning**:

1. **Retrieval (поиск):**

* из вакансии делается **“поисковое представление”** (ключевые поля),
* оно векторизуется,
* затем выполняется поиск ближайших резюме в **Pinecone**.

2. **Reasoning (объяснение):**

* агент формирует финальный ответ человеку: **почему кандидат подходит/не подходит**.

## 🧱 Workflow в n8n

### 🧭 Логика прохода 

Workflow принимает файл вакансии в Telegram, извлекает текст, превращает текст вакансии в **структурированный профиль** (навыки/опыт/ограничения/ключевые слова), затем делает **векторный поиск** по резюме в Pinecone и отправляет пользователю **топ кандидатов** с объяснением.

### 🔩 Ноды и фукнкции

|  # | Нода                               | Назначение                         | Что делает на выходе                        |
| -: | ---------------------------------- | ---------------------------------- | ------------------------------------------- |
|  1 | Telegram Trigger                   | Точка входа                        | получает `message` + `file_id`              |
|  2 | Get a file                         | Скачать вакансию из Telegram       | отдаёт файл как `binary`                    |
|  3 | Extract from File                  | Извлечь текст из файла             | `binary → extracted_text`                   |
|  4 | Information Extractor              | Извлечь структуру вакансии         | формирует `vacancy_profile`                 |
|  5 | AI Agent (+ Tool: Pinecone)        | Управляет поиском и ответом        | делает retrieval + формирует `final_answer` |
|  6 | Pinecone Vector Store + Embeddings | Семантический поиск по базе резюме | возвращает top-K совпадений                 |
|  7 | SendMessage                        | Ответ пользователю                 | отправляет итоговый текст                   |

### 🛠️ Вспомогательные компоненты
| Компонент                        | Назначение                                                                                                                                       |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| OpenRouter Chat Model1           | LLM-модель (GPT-4.1-mini), подключаемая к ноде **Information Extractor** для формирования саммари/структуры вакансии                             |
| OpenRouter Chat Model            | LLM-модель, подключаемая к ноде **AI Agent** в качестве основной чат-модели для принятия решений и генерации ответа                              |
| Simple Memory                    | Буфер “оконной” памяти, позволяющий агенту сохранять контекст диалога между итерациями                                                           |
| Pinecone Vector Store            | Векторная база данных, хранящая эмбеддинги резюме кандидатов для семантического поиска                                                           |
| Embeddings HuggingFace Inference | Модель генерации эмбеддингов (HuggingFace), используемая для векторизации запросов и документов *(transformer: distilbert-base-nli-mean-tokens)* |

## 5. 🧪 Эксперименты и гипотезы

В проекте тестировались разные способы представления вакансий и резюме так, чтобы семантический поиск работал лучше.

### ✅ Гипотезы, которые проверяли

1. **H1: “Полный текст” лучше всего отражает смысл**
   → сравнивали вакансии и резюме как есть (без извлечения структуры), используя разные embedding-модели.

2. **H2: LLM-саммари лучше вычленяет главное и повышает качество матчинга**
   → делали summary вакансии/резюме через LLM и сравнивали уже сжатые тексты.

3. **H3: Эвристическое саммари (без LLM) даст более стабильный и воспроизводимый результат**
   → пробовали эвристическую суммаризацию как “дешёвую и детерминированную” альтернативу LLM.

4. **H4: Извлечение навыков (skills) и структурирование требований улучшит сигнал и уменьшит шум**
   → сравнивали не весь текст, а наборы ключевых полей на основе заданных словарей.

5. **H5: Трюки предобработки (например 3-граммы) улучшат сопоставление**
   → пробовали внешнюю токенизацию по n-граммам перед формированием эмбеддингов.

## 6. 📏 Метрики и результаты

При оценке использовались **метрики согласованности** между:

* **ручными аннотаторами** (2 человека),
* и **автоматическими ранжировщиками** (разные варианты векторизации/обогащения текста).

### Что оценивали аннотаторы

Есть набор кейсов вида:
**(вакансия → 5 резюме-кандидатов)**, где нужно расставить кандидатов по релевантности (ранги 1..5).
Два ручных аннотатора дали свои ранжирования, а разные автоматические методы — свои.

### Какие метрики использовали

* **Krippendorff’s alpha (ordinal)** — измеряет согласованность оценок как порядковых (чем выше, тем лучше; 0 — примерно “слабое согласие”, отрицательные — хуже случайного/противоречиво).
* **Cohen’s kappa (linear weights)** — согласованность двух “оценщиков” с учётом порядковости.

## 7. 🏁 Почему выбрали “структуру по паттернам”

Финальная версия, на которой решили остановиться для рабочего прототипа (и для n8n-пайплайна), — это подход:

> **извлечь структуру вакансии (навыки/ключевые требования) по паттернам → векторизовать → искать в Pinecone → потом формировать ответ пользователю.**

Причины выбора:

1. **Лучшее качество по метрикам согласованности**
   Вариант **miniLM_L6_V2_patterns** дал **наивысшую и устойчивую** альфу Криппендорфа ~**0.30** (в сравнении с аннотатором 1), что выше остальных протестированных способов.

2. **Стабильность результата**
   “Полный текст” и некоторые варианты обогащения могут давать нестабильность: много “шума”. Чёткая структура с заданными полями устойчивее и лучше переносится между вакансиями.

3. **Контролируемость и воспроизводимость**
   Паттерны/правила дают **детерминированный** слой: проще объяснить, повторить и отладить, чем LLM-саммари (которое может меняться от запроса к запросу).

4. **Дешевле и быстрее в прод-контуре**
   Если структура вытаскивается правилами, LLM можно оставить только на этап формулировки объяснения пользователю.

## 8. 🧩 Кратко про метод “извлечение структуры по паттернам”

**Идея:** вместо сравнения *всего текста* вакансии и резюме мы извлекаем **структуру навыков (skills)** по словарю regex-паттернов и сравниваем уже “чистый сигнал”.

### 8.1. Как извлекаются навыки (skills)
В `vectorization/scills.py` задан набор паттернов `SKILL_CATEGORIES` 

* 🧑‍💻 **Языки**: `python`, `java`, `javascript`, `typescript`, `csharp`, `cpp`, `go`, `php`, `sql`…
* 🧩 **Фреймворки**: `react`, `angular`, `django`, `spring`, `.net`, `nodejs`, `drupal`, `webapi`, `entity_framework`…
* 🗄️ **Базы данных**: `mysql`, `postgresql`, `mongodb`, `redis`, `mssql`, `elasticsearch`…
* ⚙️ **DevOps-инструменты**: `docker`, `kubernetes`, `aws`, `terraform`, `cicd`, `tfs`…
* 🖥️ **ОС**: `linux`, `unix`, `windows`
* 🧠 **Методологии**: `agile`, `scrum`, `kanban`, `tdd`, `sdlc`, `oop`, `solid`

Также заложены паттерны под:

* **опыт** (`EXPERIENCE_PATTERNS`, например `5+ years…`)
* **образование** (`EDUCATION_LEVELS`, bachelor/master/phd)

Функция `extract_skills(text, all_patterns)`:
- нормализует текст,
- ищет совпадения по regex,
- возвращает **отсортированный список skills** строкой через запятую.

Пример на длинной “шумной” вакансии:  
`agile, angular, dotnet, entity_framework, express, javascript, jquery, mssql, mvc, oop, scrum, sdlc, solid, tfs, wcf, webapi`

### 8.2. Режимы: эксперименты vs демо
В ходе работы прорабатывались два разных сценария:

#### A) **Экспериментальный режим (резюме → вакансии)**
- В Pinecone загружались **5 вакансий** (каждая — отдельный вектор).
- Далее **в цикле прогонялись все резюме**: для каждого резюме строился запрос и возвращался **top-5 вакансий**.
- На лучшем варианте **навыки извлекались и для вакансий, и для резюме**.
- Результат формировался как **таблица рангов** и передавался в расчёт метрик.

**Эмбеддинги и Pinecone:**
- Embedding-модель: `all-MiniLM-L6-v2` (dim=384)
- Метрика: `cosine`
- Индекс (пример): `res-vac-match-2-scill`


#### B) **Демо-режим (вакансии → резюме)**
- Планируемый рабочий сценарий для n8n: пользователь отправляет **вакансию**, система ищет **резюме**.
- Для этого в Pinecone должен быть **индекс резюме** (с извлечёнными навыками).  


**Metadata:**
- `text` = `job_title + job_description` (единый текст вакансии)
- `source` (источник/тип документа)
